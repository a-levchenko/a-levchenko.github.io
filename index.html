4. Pitfalls → agent-memory/pitfalls.md
   - Copy the list below, one line each, tagged [<today> | WARMUP | human] (source: the facilitator's dry run).

   1. sf.js on Windows splits quoted multi-word values. Wrap them in literal double quotes inside single quotes, e.g. --query '"SELECT Id FROM Organization"'.
   2. sf.js allows only: data query, apex run/get test, project deploy start/validate/report/preview, project retrieve start/preview, sobject describe/list, org display/list, org assign permset. Its sobject describe and org list metadata output is truncated; use EntityDefinition / FieldDefinition queries instead.
   3. EntityDefinition queries reject OR. Use InternalSharingModel / ExternalSharingModel; there is no DefaultSharingModel column.
   4. Run Code Analyzer directly, not via sf.js (the wrapper forces --json): sf code-analyzer run --workspace <path> --rule-selector Recommended --severity-threshold 2.
   5. PMD EagerlyLoadedDescribeSObjectResult is High severity and blocks the edit hook. Use getDescribe(SObjectDescribeOptions.DEFERRED).
   6. Newly deployed custom fields have no field-level security for anyone, including System Administrator. CLI queries fail with "No such column" until a permission set grants the field. USER_MODE queries, "as user" DML, FeatureManagement.checkPermission and $Permission rules evaluate the context user.
   7. Test pattern: System.runAs applies sharing only, not object or field permissions.
      - In @TestSetup, tests create their own System Administrator user that holds the feature's permission set, and run every arrange and assert step in runAs(that user).
      - Persona users run in separate, non-nested runAs blocks.
      - Setup-object DML goes inside runAs(new User(Id = UserInfo.getUserId())).
      - Never rely on the running user's permission sets.
   8. project deploy validate rejects --test-level NoTestRun. Use RunSpecifiedTests --tests <class>.
   9. CreatedDate cannot be placed on a page layout; use CreatedById, which shows the name and date. Related lists and list views use CREATEDBY_USER and CREATED_DATE, never CREATEDBY_ID.
   10. Apex that references Label.* must deploy together with, or after, the labels. A failed deploy rolls back everything.
   11. A matching rule activates about a minute after deploy. Its duplicate rule deploys only after MatchingRule.RuleStatus = Active.
   12. A unique-field violation returns DUPLICATE_VALUE; an active duplicate rule returns DUPLICATES_DETECTED.
   13. DateTime fields drop milliseconds; allow a one-second margin in test assertions.
   14. sf template generate is blocked by the shell hook. Specify metadata fully and check it with project deploy validate. A FlexiPage references a custom LWC as c:<name>.
   15. The platform "Analytics Cloud Integration User" profile automatically gets Read on new custom objects. Mention it whenever promising that only certain users can see data.
   16. Sample org metadata with: sf.js project retrieve start -m "<Type:Name>" --output-dir <scratchpad>. Never retrieve into force-app.

/sf-task Task: WS-<INITIALS>. Org: <ORG_ALIAS>. Base branch: main. Title: Equipment lending register (lean).

Our office lends company equipment to employees: laptops, projectors, test devices, tools. Today it is a spreadsheet at reception and things go missing. We want a register of the equipment we own and who has what right now. Reception must be able to hand an item out and take it back, and see which items are overdue. An item that is already out must not be handed out to someone else until it has been returned.

BUSINESS DISCOVERY INTERVIEW (Phase 0.1b). Run it exactly as scripted below.
- Ask every question through the interactive question tool, in the rounds shown (3 questions per call).
- Use the options as written: the first option is the recommended one and is labelled "(Recommended)"; the text after the dash is the option's description.
- Do not skip a question because the request seems to answer it, and do not add business questions unless an answer leaves a real gap.
- If I choose a non-recommended option or "Other", follow my answer. Tell me in one plain sentence that it makes the build bigger, then continue.
- Record every question and answer verbatim in request/01-clarifications.md.
- Then write the scope document. Its "What is NOT part of this" includes the defaults listed after the questions, unless an answer brought one into scope.
- Read the scope back to me in one question, then do the mandatory confirmations (org, branch, base branch).

Round 1: people
Q1. Who will use this in Salesforce, and who keeps the equipment register up to date?
  - Reception + office manager (Recommended) — reception hands out and takes back; one office manager adds equipment and retires items; reception cannot change the register.
  - Reception does everything — simpler access, but anyone at reception can change or remove items.
  - Several teams — more teams lend equipment; each needs the same access.
Q2. Do the employees who borrow equipment have their own Salesforce login?
  - No, most don't (Recommended) — we keep a simple list of employee names; reception can add a new name on the spot.
  - Yes, everyone has a login — reception picks from Salesforce users; people without a login cannot borrow.
Q3. Do employees need to see anything themselves?
  - No, staff only (Recommended) — only reception and the office manager use it.
  - Yes, they see what they hold — needs logins for every employee and an extra screen.

Round 2: the lending process
Q4. How does an item become "overdue"?
  - Return date per hand-out (Recommended) — reception enters a return date each time; the item is overdue the day after if not back.
  - Same loan period for all — a fixed number of days for every item.
  - Return date optional — long-term loans have no date and are never overdue.
Q5. Do you want a history of who had each item, or only who has it now?
  - Keep full history (Recommended) — every hand-out and return is kept: who, when, and who at reception handled it.
  - Only the current holder — past loans are not kept.
Q6. Should anyone be reminded automatically about overdue items?
  - No, a list is enough (Recommended) — reception sees an overdue list and follows up; no emails.
  - Email the borrower — needs an email address for every employee.
  - Daily email to reception — a summary email in addition to the list.

Round 3: rules and mistakes
Q7. What happens when an item is lost, broken or no longer used?
  - Office manager retires it (Recommended) — it stays in the register but can no longer be handed out.
  - Not needed now — items are only ever available or out.
Q8. If someone records a hand-out or return by mistake, who fixes it?
  - Reception or office manager, history shows it (Recommended) — both can edit a loan; every change is recorded with who and when. Simplest.
  - Only the office manager — reception can only hand out and take back; needs an extra rule and special access (bigger build).
Q9. When someone tries to hand out an item that is already out, what must they see?
  - A refusal is enough (Recommended) — the save is blocked with a standard "duplicate" message.
  - A message naming who has it — "already out with <name>"; needs extra programming (bigger build).

Round 4: the screen and the data
Q10. What should reception work in?
  - Standard Salesforce pages (Recommended) — item and loan pages with buttons and ready-made lists; fastest to build.
  - A custom reception screen — one page with search-as-you-type and status per item; roughly doubles the build.
Q11. How does reception find the right item?
  - Search by asset tag or name (Recommended) — Salesforce's standard search; no scanner needed.
  - Barcode scanning — needs scanners and labels on every item; a bigger build.
Q12. What about the items in today's spreadsheet?
  - Enter or import later, not in this build (Recommended) — entered by hand or imported by an administrator with standard tools after go-live.
  - Include a one-time import — you provide the file; adds clean-up and loading work.

Round 5: scale, place, done
Q13. How much equipment and activity are we talking about?
  - Hundreds of items, a few loans a day (Recommended) — up to a few hundred items and employees, a handful of hand-outs per day.
  - Thousands of items, dozens a day — needs extra attention to search and volumes.
Q14. Where should reception find this in Salesforce?
  - Its own Equipment app (Recommended) — a separate app with tabs for items, employees and loans.
  - Inside an existing app — tell us which one.
Q15. How will you check that it is done?
  - Walk-through in the sandbox (Recommended) — add an item, hand it out, see a second hand-out refused, take it back, see an overdue loan, retire an item.
  - Walk-through, then reception tries it for a few days — the same, plus a trial period before sign-off.

Default "not part of this" (state these in the scope; do not ask):
- quantities or stock counts
- condition or damage notes
- booking in advance
- reports and dashboards beyond the lists
- a mobile layout
- deleting loans
- a separate "asset tag already used" message (the unique tag check is enough)

HOW TO RUN THE REST OF THIS TASK. These are my decisions as the owner, to keep total agent time near one hour:
1. Discovery: project memory is pre-filled; reuse it. Verify only what this design depends on: names free, no automation on objects you touch, licence facts. Do not inventory unrelated org metadata.
2. Brief: at most 2 pages, simplest design that meets the confirmed scope, declarative first.
   - I waive these defaults: the permission-persona test matrix (keep the one mandatory negative permission test), LDV/archival planning, and separate selector/service/constants classes where one small class is enough.
   - Use Apex only for what declarative tools cannot do (with the recommended answers: only the one-open-loan guarantee). No Flow.
3. Critic: round 1 on the brief only. The architect resolves the gaps. No round 2 unless round 1 finds a G1.
4. Detailed design: compact, at most 2 pages. Specify only what the brief does not already fix, in at most 2 work packages (3 if I chose a custom screen). Buildability check in a single pass.
5. Build: tests first. Use the test-user pattern in agent-memory/pitfalls.md: tests create their own admin and persona users and never rely on the running user's permission sets.
6. Review: send only S1/S2 findings back to the developer. List S3/S4 in the final report instead of fixing them. Stop after round 1 if the verdict is APPROVE or APPROVE WITH CHANGES.
7. Handover: deployment package as standard. Administrator and user guides at most 1 page each.
